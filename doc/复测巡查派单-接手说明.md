# 复测与巡查安排单·夜间走表 — 接手说明

> 给新来的人：先读这一篇，再动代码。这一块的所有「口径」（窗口、到期、提前、挑谁、
> 落成什么记号、趟末报哪三个数）只有一处出处，其余地方一律不许另算。

## 一句话形状

复测通知与现场巡查**同在一张表 `t_nslp_task_item` 上，一行一事，夜里走一趟**。
每天只在 **02:00–05:00**（含 02:00、不含 05:00）这一截动手；窗外任何触发只答话、
一行不动。一趟至多派 **500** 行，装满即止，剩下的下趟接着挑。

## 唯一口径出处

`src/main/java/com/fc/v2/service/support/TaskDispatchRules.java`

纯 Java、不碰库、不沾 Spring，所有判断只在这里作答，类注释里把每条规则都钉死了。
改规则只改这一处，配 `TaskDispatchRulesTest`。**不要在 Service / Controller / SQL 里再写第二遍。**

| 问的事 | 唯一方法 | 定死的取法 |
|---|---|---|
| 这截开不开 | `isOpen(at)` | 小时 ∈ [2,5)；`at=null` 算关 |
| 到没到期 | `isDue(eff, at)` | `eff <= at`，**恰好相等算到期** |
| 可提前几日 | `earlyDaysOf(amount)` | 空/负/零→0；小数向零取整；封顶 3660 日 |
| 真正可办时刻 | `effectiveDueAt(due, amount)` | 往回数「可数日」，时刻不动 |
| 可数日 | `isCountableDay(d)` | 扣掉周六周日、`STATUTORY_HOLIDAYS`（2026 一册） |
| 还搁着没有 | `isWaiting(status)` | **status=0 或 NULL 都算搁着**（见下「存量老数据」） |
| 本趟挑不挑 | `pickable(...)` | 搁着 + 未删 + 到期 |
| 先办谁 | `comparePickOrder(...)` | 最到期在前，同刻按主键 |
| 发给谁 | `recipientOf(createBy)` | 只认本行 `create_by`，空白→发不成 |
| 三数→答话 | `replyOf(picked, sent, failed)` | 没动单固定回「本轮未改动安排单」 |

## 两条进入路径，落到同一处

```
HTTP  POST /nslpTaskItemDispatch/run
        └─ NslpTaskItemDispatchController
             └─ ITNslpTaskItemDispatchService.runOnce(at)   ← 真正的夜间走表
                    TNslpTaskItemDispatchServiceImpl

Quartz 按 bean 名反射触发（见 t_sys_quartz_job.invoke_target / JobInvokeUtil）
        └─ 老的 ITNslpTaskItemService（TNslpTaskItemServiceImpl）
             ├─ listDue(at) ：照 TaskDispatchRules.pickable 取（窗外回空表）
             └─ runOnce(at) ：直接委托 ↑dispatch，返回「发出几行」
```

- 控制器只注入 dispatch；老接口 `ITNslpTaskItemService` 在主代码里**已无别处调用**，
  它只是留给库里可能仍存在的、指向 `…TaskItemService.runOnce` 的定时作业行一个不会闯祸的落点。
- 配置新定时任务时，触发目标写走表那一处；窗口由口径自己把，cron 即使写错时段也不会动数据。

## 一趟是怎么走的（`TNslpTaskItemDispatchServiceImpl.runOnce`）

1. `isOpen(press)` 关外：窗外直接回 `of(0,0,0)`，不查库、不动行。
2. 预筛「仍搁着且未删」：SQL 条件 `del_flag=0 AND (status=0 OR status IS NULL)`。
3. 逐行用 `pickable` 判到期（内存，含提前/节假日），再按 `comparePickOrder` 排序。
4. 逐行处理，每行动手前再看一次墙钟，过 05:00 立即收手：
   - 办成：一句 UPDATE 同时落两处记号——`status=1`＋`content` 追加「［已发出 时刻 发给 谁］」。
   - 一行站不住：只把本行 `status=2`、`remark` 写失败原由；**其余行照常，整趟不中断**。
5. 两处 UPDATE 都带「仍搁着」守卫（`waitingGuard`：`id` + `del_flag=0` + `(status=0 OR status IS NULL)`）。
   - 并发两趟 / 同趟重复：只有一趟咬得住，咬不住的不算发出也不算失败 → **幂等**。
   - 空状态老行发成后 status 变 1，第二回再也咬不住。
6. `picked/sent/failed` 在这一遍里累计，`TaskDispatchResult.of(...)` 同次产出答话，不另起一轮点数。

## 存量老数据（取舍已定死，别再摇摆）

`t_nslp_task_item.status` 列是 `DEFAULT NULL`（见 `doc/schema/nslp.sql`）。老系统迁来的行
这一格常空。**定死：空情形 = 从没办过 = 按「搁着」对待**，和显式 0 一条待遇。

- 取舍理由：这张表的「已办」凭证是 status=1/2；NULL 绝不可能表示已办，只会是漏填。
  若把 NULL 当不明而跳过，老的复测条目会永远发不出去（台账到期、夜里不发）。
- 只有「挑得中」放宽到 NULL；**落记号仍是条件更新**，所以放宽不会造成重复发。
- 一条复测条目「该照哪版走」也由此定死：**无论新老，一律走 `TaskDispatchRules` 现行口径**，
  不存在「老行按老算法」的分支。

## 当初的坑（都在老 `TNslpTaskItemServiceImpl` 里，现已统一掉）

- 别的时段触发也照动数据 —— 老实现没有 `isOpen` 窗口判断。
- 已处理条目重复参与 —— 老实现 `selectList` 全表、不看 status/del_flag。
- 恰好到期结论两样（今天/明天、明天/后天对不上）—— 老实现用严格 `<`，新口径是 `<=`。
- 空集合越界 —— 老实现 `due.get(0)`，空单直接 IndexOutOfBounds。
- 空 amount 空指针 —— 老实现 `getAmount().signum()`。
- 状态不更新、两处数合不上 —— 老实现只点数不落库，处理过也还是「搁着」。
- 一条异常整趟打回 —— 老实现没有逐行容错。

新实现对应的回归用例都在 `TNslpTaskItemDispatchServiceImplTest`（含 NULL 老行的
发出 / 幂等 / 无收件人标失败）和 `TNslpTaskItemServiceImplTest`（窗外不动、空单安全、委托）。

## 改这块时的自检

- `mvn -Dtest=TaskDispatchRulesTest,TNslpTaskItemDispatchServiceImplTest,TNslpTaskItemServiceImplTest test`
- 全量：`mvn test`（当前 165 个用例全绿）。
- 任何「到期/搁着/窗口」的改动，先想 `TaskDispatchRules`，并补规则级纯单测；
  Service 只落库装配，别在里面写判断。
